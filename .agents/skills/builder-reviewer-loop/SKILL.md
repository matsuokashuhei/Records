# ビルダー / レビュアー ループ

2体のサブエージェントで実装を進め、メインエージェント(あなた)は
オーケストレーションと最終検証だけを行う。
ゴールはレビュアーの判定が **合格** になること。それまでループを繰り返す。

## 役割

- **ビルダー**(`subagent_general`、書き込み可): 実装、xcodegen、ビルドを
  実行し、結果を報告する。
- **レビュアー**(`subagent_explore`、読み取り専用): 実際のコードを要件・
  プロジェクトのスキル・AGENTS.mdのルールに照らして検査する。
  ファイルの編集は絶対にさせない。
- **メインエージェント**(あなた): 依頼を要件リストに分解し、ブリーフを書き、
  レビュー指摘を`resume`でビルダーに中継し、最後に自分で実機検証する
  (ビルド状況・ログ・再起動)。

## 手順1: 要件ブリーフを作る

- まず関連コードと`AGENTS.md`を読む。ユーザーの依頼を番号付き要件リストに
  変換する — レビュアーはこのリストそのものに対して採点する。
- 合致するスキル(`skill`ツール)を読み込み、そのチェックリストを
  レビュアーのブリーフに入れる(例: ガラス系なら`swiftui-liquid-glass`、
  品質レビューなら`review-and-simplify-changes`のrubric)。

## 手順2: ビルダーを起動する

`run_subagent`に`profile: subagent_general`を指定。ブリーフに必ず含めるもの:

- 番号付き要件(採点できる粒度でそのまま書く)。
- AGENTS.mdの鉄則を引用して書く(ビルダーが見落とせないように):
  - すべてのUIアクションと非同期処理に`os.Logger`を仕込む。
    subsystemは`com.cacheandbuffer.Records`、文字列補間は`\(v, privacy: .public)`。
  - ファイルの追加・削除・リネーム後は必ず
    `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodegen generate`
    を実行する。project.pbxprojの手編集は禁止。
  - `RecordsApp.init`内の`Records --catalog-test <URL> [--play]` CLI経路を
    壊さない。
- ファイルマップ: `Records/`(アプリUI)、`Shared/`(アプリとウィジェット
  双方にリンク — ここを変えるとウィジェットに影響)、`project.yml`。
- ビルドコマンド:
  `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild -project Records.xcodeproj -scheme Records -configuration Debug -derivedDataPath .build build`
- ビルダーはUIを目視できないこと — スクリーンショットではなく
  コンパイル+ログで検証するよう指示する。
- 報告フォーマット: 変更/新規/削除ファイル一覧、設計上の主要な選択、
  ビルド結果。

## 手順3: レビュアーを起動する

`run_subagent`に`profile: subagent_explore`を指定(読み取り専用が必須 — 
編集・xcodegen・コミットをさせない)。ブリーフに必ず含めるもの:

- ビルダーと同じ番号付き要件(合否チェックリストとして)。
- 該当スキルのチェックリスト(チェック節を貼るか、スキルファイルの
  パスを指す。例: `.agents/skills/<name>/SKILL.md`と`references/`)。
- 照合するAGENTS.mdルール: ログ網羅性、xcodegen/pbxprojの整合
  (新規ファイルがSourcesビルドフェーズに含まれるか、手編集の痕跡が
  ないか)、`--catalog-test`が無事か。
- レビューrubricのカテゴリ: 再利用 / 品質 / 効率 / 明瞭性 / 動作リスク。
- 判定フォーマット: 冒頭に`合否判定: 合格 / 条件付き合格 / 不合格`、
  続けて各指摘を`ファイル:行 — カテゴリ — 問題 — 推奨修正 — 確信度`の形で。
- 合格条件: 全要件を満たす、かつhigh確信度の指摘がゼロ。
  medium/lowだけの場合は条件を明記した上で条件付き合格でもよい。

## 手順4: 中継してループする

- 合格なら手順5へ。
- それ以外: `run_subagent`を`resume: <ビルダーのagent_id>`付きで呼び、
  指摘をそのまま中継する(必須と任意を区別して)。その後
  `resume: <レビュアーのagent_id>`で再レビューさせる — ビルダーの
  報告ではなく実コードで各修正を検証し、リグレッションも見るよう指示。
- `resume`(継続)を使うとコンテキストが保たれる。出力が混乱・矛盾
  してきた場合だけ新規エージェントに替える。
- 上限: 同じ指摘が2ラウンド直らなかったらループを止め、回り続ける
  よりもユーザーに報告して判断を仰ぐ。

## 手順5: 完了報告の前に自分で検証する

サブエージェントはUIを見られず、古い状態を見落とすことがある — 
必ず自分で確認する:

- 起動中のアプリが古いバイナリのことがある。`open .build/Build/Products/Debug/Records.app`
  の前に`pkill -x Records`すること。さもないと`open`は古い
  インスタンスを活性化するだけになる(実際に一度起きた)。
- 期待するログ行が出ているか確認:
  `/usr/bin/log show --last 2m --style compact --info --predicate 'subsystem == "com.cacheandbuffer.Records"'`
  (debugレベルを出すには`--info`が必要)。
- `git status`でファイル一覧がビルダーの報告と一致するか照合。
- 画面キャプチャは権限がなく使えない — 見た目はユーザーに確認を
  頼み、どこを見ればよいか具体的に伝える。

## アンチパターン

- レビュアーにファイルを編集させない — 報告だけさせる。
- ビルダーの報告だけで完了にしない — レビュアーと手順5を必ず通す。
- ビルダーのビルドがグリーンになる前にレビュアーを起動しない。
- ビルダーに曖昧な指示を出さない — 要件リストが契約書である。
